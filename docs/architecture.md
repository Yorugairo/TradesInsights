# Architecture

> Maintained as a deliverable: update this file whenever the workspace structure, data flow, or a package's responsibility changes. Last updated: M0 (2026-07-15).

## System flow (spec §4)

```
official source
  → scheduled source run (pg-boss job or CLI)
  → immutable raw artifact (MinIO/S3, content-addressed by SHA-256) + raw_artifacts row
  → format parser (adapter.parse)
  → NormalizedSourceRecord (Zod-validated at the runner boundary)
  → source_records upsert + evidence_items          [built: M0]
  → address/parcel/organization normalization        [M2]
  → project resolution → project event timeline      [M2]
  → account route + deterministic score              [M3]
  → evidence verifier → review queue                 [M3]
  → digest/alert → customer feedback                 [M3]
```

## Key mechanisms (M0)

- **Immutable artifact store** (`source-sdk/object-store.ts`): objects are content-addressed (`raw/<sourceKey>/<sha256>`), so identical content is stored once and existing content can never be overwritten with different bytes. `raw_artifacts` has a unique index on (source, canonical URL, sha256).
- **Run orchestrator** (`source-sdk/runner.ts`): discover → fetch → store-before-parse → Zod-validate → upsert by (source, external_id) with a normalized fingerprint for change detection. Metrics per run: discovered / fetched / unchanged / parsed / rejected / duplicate / errors. Per-item failures become dead-letter entries in `source_runs.metrics_json` with enough context to reproduce.
- **Idempotency**: rerunning against unchanged content yields `unchanged` counts, bumps `last_seen_at`, and creates no new rows or objects (proven by `apps/worker/test/m0-exit-gate.test.ts`).
- **Durable jobs** (`apps/worker/src/jobs.ts`): pg-boss queues on the same Postgres; `source-run` retries with exponential backoff, exhausted jobs land in `source-run-dead-letter` with payload intact.
- **Health** (`source-sdk/health.ts`): green/amber/red per spec §14, persisted to `coverage_entries.freshness_state`.
- **Parser replay** (`source-sdk/replay.ts`, D5): `replaySource` re-parses a source's stored immutable artifacts through the current adapter and rewrites only the derived `source_records.normalized_json` where the new parse differs — so a parser fix heals history without re-fetching (the immutable store becomes a correctness asset, not just an audit log). Raw artifacts are read-only; evidence is append-only (backfilled only when absent); idempotent under an unchanged parser. `raw_artifacts.discovery_meta_json` persists the discovery-time context so the re-parse is faithful. `pnpm source:replay <key>`.
- **Parser self-reconciliation invariants** (`source-sdk/invariants.ts`, D1 — decision of record): positional PDF/table parsers assign values by geometry, so a layout shift can silently mis-assign a column without changing any field name, dropping volume, or emitting zero records — the schema-fingerprint, volume, and zero-record health checks all stay green through it. To close that hole an adapter may implement the optional `checkInvariants(raw, parsed, ctx)` hook; the runner calls it per artifact after persistence, records violations in `source_runs.metrics_json`, and `evaluateSourceHealth` turns the source red on any. The strongest invariants reconcile the parse against the document's *own printed totals* by an independent text search (Lacey census: printed permit count, dwelling-unit total, valuation grand total), so a geometry drift is caught by divergence from a number the parser reads a different way. Records are not dropped on violation — red + the §15 gate's red-source suppression withhold delivery until a human confirms.
- **Model gating** (`apps/worker/src/env.ts`): boots without model keys; model-dependent jobs report a visible blocked state (also blocked when `LLM_MONTHLY_BUDGET_USD` is unset).
- **Structured logs**: pino JSON with `traceId`, `sourceRunId`, `jobId` bindings; sensitive headers/params redacted (`source-sdk/logging.ts`).

## Decisions of record

- **No Redis** — pg-boss on Postgres (spec §2).
- **Content-addressed storage keys** rather than mutable paths: immutability is structural, not procedural.
- **Adapters never create opportunities** — they stop at `source_records` + `evidence_items` (spec §5).
- **Sources ship disabled** — `config/sources.yaml` requires terms/robots review dates before `enabled: true` (validated by the config loader).
- **Solicitations are a SECOND record class, not permits** (owner decision, 2026-07-27). `NormalizedSolicitationRecord` + `insights.solicitations`, carried through the same source pipeline. A bid disagrees with a permit on every structural axis: `county` is required+enum on the permit record and routinely absent here (statewide procurement); the defining date is a bid DEADLINE, which has no permit column; and a bid ends in a WINNER. Two event types that already existed — `bid_deadline_changed`, `award_published` — could never fire in the permit model for exactly that reason. **The seam is one branch in `runner.ts` plus one table**: discover/fetch, fetch policy, artifact store, replay, backfill, the `source_runs` lifecycle and counters, health, orphan reaping, config and alerting are all record-type-agnostic and reused unchanged. The union lives at the `SourceAdapter` boundary (`ParsedRecord`) rather than inside `ParsedSourceRecord`, so all 36 existing adapters compile untouched — verified, zero adapter edits.
- **The solicitation dedupe key excludes `observed_at`, inverting 0035.** An event is append-only, so a re-emit is new information and `observed_at` had to be in that key (136 real re-emits depended on it). A solicitation is a MUTABLE row: an amended bid is the same solicitation with a later deadline, so keying on `observed_at` would create a new row every run. Amendment history belongs in `project_events`.
- **Scheduling lives outside the process** (`.github/workflows/source-fleet.yml`). `registerSchedules()` is correct but needs a long-running host, and nothing ever created the `pgboss` schema, so it had never initialized — every production run before 2026-07-27 was manual. GH Actions runs each cadence set SEQUENTIALLY via `pnpm source:run:cadence`, which honours the per-source stagger's purpose (one county server at a time) more strictly than the stagger did, without pretending to a cron precision GH does not have.
- **Geometry columns** exist from M0 (PostGIS `geometry(Geometry,4326)`), but read/write handling arrives with M2 resolution work.
- **Verified decision brief** (`packages/intelligence/src/brief.ts`, decision of record) — the only place model PROSE reaches the customer. It is a rendering of already-verified rows, never a source of truth: the model composes from a fixed menu built entirely from the deterministic decision memo (verified facts, labeled inferences, deterministic context), and `validateBrief` rejects the whole draft on an unknown ref or an unsubstantiated number/date (the §13 "reject unknown evidence IDs" rule applied to prose). Segment kind is DERIVED from cited refs, so an inference can never be surfaced as a fact. Persisted as an account-scoped `model_runs.job_type='brief_draft'`; a rejected/blocked draft falls back to the deterministic memo. Scores, stages, and `bidding_confirmed` still come only from stored data — prose never sets them.
- **First-look coverage metric** (`packages/delivery/src/leadtime.ts` `firstLookByCoverage`, decision of record) — the "we see it first" number, a THIRD lead-time framing alongside evidence-lead and detection-lag: per source×county, how often our earliest sighting predates the `permit_issued` (publicly biddable) milestone and the median lead when early. `permit_issued` is the public-visibility proxy (a permit surfaces on aggregator bid boards). Same no-fabrication conventions: stated-date anchored, floored at 0, sample floor, test sources excluded, groups below floor dropped.
- **Pipeline summary** (`packages/delivery/src/pipeline.ts`) is a COMPOSITION over existing S5 machinery (pursuit state machine, `opportunity_outcomes`, evidence lead, first-look), not a new store — the customer-facing sourced→bid→won funnel + dollar attribution, reproduced from stored rows only.
- **De-routing archives, it does not invent a state** (`packages/intelligence/src/score-run.ts`, decision of record, 2026-07-26, code landed in `fb200c5` — see STATUS.md "Commit provenance") — `scoreAll` used to write only the pairs `routeProject` RETURNED, so an opportunity whose (project, account) pair stopped routing (territory edit, exclusion rule, keyword reclassification) kept its row untouched at its last score and algorithm version forever. Found live: opportunity `93054ce2` (solis_interiors, `weekly_digest`, 72.5) still carried `algorithmVersion` 1.9.0 three releases after 1.12.0. The run now sweeps at the end and moves de-routed rows to **`archive`**, recording the reason under `rationale_json.deroute` (`reason`, `archivedAt`, `previousState`, `atAlgorithmVersion`). `archive` was chosen over a new "stale" flag because it is already this system's word for "scored, not deliverable" and every delivery path honours it. Three constraints hold the sweep honest: it only considers pairs whose project the run actually re-scored (a scoped or aborted run can never archive what it did not read); it skips accounts with no router in `ROUTERS`, since "nothing routed" there is a config gap, not a verdict; and it never touches `dismissed`/`promoted`, re-asserting that guard at write time so an owner acting mid-run wins. The marker is merged into the rationale, never over it, and is cleared automatically if the pair routes again.
- **Delivery refuses a score it cannot name** (`scoredByCurrentAlgorithm`, decision of record, 2026-07-26, code landed in `fb200c5` — see STATUS.md "Commit provenance") — the weekly digest and the WS-C phase-change alert both withhold an opportunity whose `rationale_json.algorithmVersion` is not the running `SCORING_ALGORITHM_VERSION`. The score is what ORDERS a digest, so a score from a retired model cannot be ranked against current ones. An ABSENT version fails too: `scoreAll` stamps every row it writes, so unknown provenance is not current provenance. This is a second, independent line to the sweep above — it also catches a rescore that dies partway and leaves mixed versions live (2026-07-26: a pooler drop after 31 of ~1,260 Solis rows). Withheld items are counted and disclosed in digest section 5 (`suppressed.staleScore`) and in `AlertsRunSummary.evaluated.staleScoreSkipped`, never silently dropped.
- **An authoritative id awaiting review outranks every weaker pass** (`resolver.ts` pass 1b `pendingReviewForSamePermit`, decision of record, 2026-07-27) — `matchByIds` can only see ids that reached `project_external_ids`, and that table is written exclusively by `registerExternalIds` from `mergeIntoProject`/`createProject`, both of which need a project. A record parked in `resolution_reviews` has no project, so **the strongest key this system has is invisible to the resolver for exactly as long as a human has not answered an unrelated question**. A second record carrying the same permit number then matched nothing and fell through to parcel, fuzzy, or `createProject` — every one a guess against a key already known to be authoritative and already known to be undecided. Measured live on the Pierce PALS hydration lane: **46 records did this — 31 created a SECOND project for a permit we already held, and 15 merged on `parcel_overlap` into a project that diverges from their twin's review candidate**; in all 46 the twin's review points elsewhere, so deciding those reviews splits one permit across two projects permanently. The record is now parked next to its twin (`official_id` / `same_permit_pending_review`, twin's candidate carried through so the rows cluster together in the cockpit). This **self-heals in both directions**: whichever way the reviewer decides, the twin lands on a project, that project registers the permit number, and the held record's next pass merges on `official_id` — nothing is stranded and no enrichment is lost, because the record and its evidence are already stored and the review row carries its features, so a licence captured for a parked permit surfaces as exactly the org support the twin was blocked for lacking. Matched on jurisdiction as well as number, since a bare permit number is only unique within its authority. **`ResolveOptions.adjudicating` is load-bearing**, not a convenience: `decideReview` marks a row `rejected` *before* re-resolving, so "has a pending review" cannot distinguish the record being decided from one merely waiting — without the flag the two records hold each other and neither can ever produce a project. Pinned by a test that asserts the deadlock.
- **`observed_at` is what separates a duplicate event from a real one** (migration `0035_project_events_unique.sql` + `emitEvent`, decision of record, 2026-07-27) — `project_events` carried only two NON-unique indexes since `0000_init`, so `emitEvent`'s bare INSERT had nothing stopping it writing the same event twice; **2,861 surplus rows of 44,111 live (6.5%)** had accumulated. The obvious key — `(project_id, source_record_id, event_type, event_date)` — is WRONG, and measurably so: it collapses 2,997 rows, i.e. **136 more than are actually duplicated**. Those 136 are `applyRecordUpdates` re-emitting for a record whose content drifted (a Seattle application becoming an issued permit on the same row), which is a real stage change, not a repeat. A duplicate is written at the same instant; a re-emit is observed later. The unique index therefore includes `observed_at`, and carries `NULLS NOT DISTINCT` because `event_date` is nullable on 383 rows and Postgres would otherwise treat every NULL as distinct and let precisely those rows duplicate freely. `emitEvent` now names that index via `ON CONFLICT DO NOTHING`, which also retires the older known gap: `resolveRecord` is still not transactional, so a fault between the event write and the resolution write still leaves the event committed and the record unresolved — but the next run's re-emit is now a no-op rather than a duplicate, and the call is safe to retry for the first time.
- **A parked review is re-asked, never timed out** (`reevaluatePendingReviews`, decision of record, 2026-07-27) — a review is a verdict on the evidence available WHEN IT WAS PARKED, and nothing re-asked the question, so the queue only grew (2,505 rows, oldest four days old) — and pass 1b deliberately routes MORE records into it. Re-evaluation runs nightly inside `runMaintenance`, positioned after `resolveUnresolved`/`applyRecordUpdates` so this run's evidence counts and before `scoreAll` so a cleared review scores tonight. **It acts only on `official_id` or `explicit_reference`** — an authoritative identifier match, never a parcel or fuzzy verdict, because those are exactly the guesses the review exists to question; auto-accepting them would be a lowered threshold wearing the costume of new evidence. Age is never an input: there is no timeout and no stale-equals-accept. WHICH decision reproduces the verdict depends on agreement — an id that AGREES with the parked candidate merges into it, one that DISAGREES rejects and re-resolves (rejection excludes the stale candidate, which is safe precisely because the strong match is a different project; merging would bind the record to the project the evidence just overruled). That second branch is the shape of all 46 split permits repaired by hand on 2026-07-27. Decisions are stamped `decided_by = 'system/reevaluation'`, so they are auditable and reversible through `undoResolution` like any human decision. To guarantee the preview and the apply can never disagree, both call ONE shared pass sequence (`decideResolution`); `previewResolution` reports its verdict and `resolveRecord` executes it, rather than maintaining two ladders that agree on the day they are written.
- **The 784 same-address name mismatches are not a name-matching problem** (measured 2026-07-27 via `pnpm review name-audit`) — the proposal was to see how many collapse under the newer `crossNameKeyLoose` + `classifyNameAgreement` containment logic. The answer is **0 of 784: 100% `none`**, and the reason is structural rather than a threshold to tune. Those strings are not business names at all, they are permit titles — `"20260190 – SFR - Remodel"` against `"20260325 – Plumbing"`. `classifyNameAgreement` exists to compare an L&I registration to a Google listing, i.e. company names; pointing it at permit titles is a category error and no loosening of it will ever help. These rows need a different signal entirely (organization names carried on the records, or parcel evidence), and the audit is retained as a read-only report so the question is answered with a number rather than re-argued.
- **Resolver failures carry their ids out of the run** (`ResolveRunSummary.errors` + `resolverErrorAlert`, decision of record, 2026-07-27) — `resolveUnresolved` logged each failure and incremented a counter, persisting nothing, so when a run reported `errors: 15` on 2026-07-27 the fifteen ids were unrecoverable: the log line had scrolled and there was no other record. They proved transient, but nothing in the system could have distinguished that from fifteen permanently malformed records. `errors` is now `{sourceRecordId, error}[]`, mirroring `BulkDecisionSummary.errors`, and a non-empty list raises a `resolver_errors` alert carrying every id. The alerts table is the durability layer rather than a new `resolution_errors` table — this is ~15 rows on a bad run against a table that already has idempotent writes, an email path and an operator surface. Its idempotency key is `(day, digest of the failing ids)`: the same records failing repeatedly in one day write one row instead of spamming, a DIFFERENT set always writes its own row so no id is ever swallowed by a dedupe, and including the day means a persistent failure re-announces itself daily instead of going quiet after first sighting. This is also the first alert derived from IN-RUN state rather than from a query, which is why `runAlerts` accepts `extraCandidates`.
- **Google Place confirmations are staged here and landed there** (`recordGooglePlaceConfirmations`, seam boundary, 2026-07-27) — `registry_partner.partner_observations` holds **7,460** `google_place_confirmation` rows, of which **3,882 sit at `applied_at IS NULL`** (every unapplied row in the whole table). This repo CANNOT land them: the consumer is the loader in the OneTradeNetwork tree, and `applied_at`/`applied_action` are its provenance — writing them from behind the seam would forge a decision the loader never made. What the loader must honour: `dedupe_key` as the identity of an (entity, place) pair; the `trust_score` tiers (0.95 exact/close, **0.9 `contained`** — the newer, weaker class, 840 rows — and 0.4 contested); `contested`, which means several licences claim one place and at most one can be right; and `name_basis`, which says HOW the names agreed so a reviewer can judge 840 containment rows as a class instead of one at a time. A further **3,578 already-applied rows predate `name_basis` and carry none**; `--restage` backfills their payload, and deliberately rewrites payload ONLY — not `applied_at`/`applied_action` (the loader's), and not `trust_score`, because silently re-scoring a decision the loader has already acted on is a retroactive edit rather than a backfill. Where the recomputed trust disagrees it is counted as `trustDrift` and reported, so the disagreement is visible and can be decided deliberately.
